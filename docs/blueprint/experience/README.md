## How to review it

1. **First visit:** start with the welcome screen; understand the product before an account or microphone request. Setup is short, skippable where possible and changeable later.
2. **Material to lesson:** choose a document or passage → compare extracted text against its page → save a reviewed revision → choose a goal and lesson form → teach → practise → keep notes.
3. **Ask the teacher:** pause, tap an anchored number, ask a typed question, choose microphone use, check a transcript, request a smaller step and resume. The board and source remain connected.
4. **Engineering and CS:** use the actual existing studio imagery and entry points. Show the motor assembled, exploded and operating; follow a software request; switch to reading if the room cannot load.
5. **Evidence to direction:** preserve working, assistance and sources → select a role → explain gaps → build a project → prepare a truthful CV → review an opportunity → retain a draft until a specific external action is confirmed.
6. **Settings and access:** language, voice, captions, motion, data use, memory, connections, privacy, reminders, security, export, deletion and sign-out are separate understandable choices.
7. **Recovery:** processing failure, service failure, expired session, microphone denial, storage failure, unsaved work and conflicting drafts have an explicit safe route onward.

The prototype uses an authored **stock-control** example: opening 20 + delivery 12 − sales 9 = expected 23; observed 22. It is not a private learner document, official memo or real employer assessment. The CV, role and opportunity entries are samples. No application is sent.

## Evidence boundaries

The HTML uses saved Rain/studio renderings copied with hashes in [asset provenance](../../../design/app-experience-20261023/assets/provenance.json). They show real existing asset/workspace foundations, not new browser acceptance or an integrated live Rain lesson. New screens, auth, sharing, unrestricted speech, multilingual speech, sync, live opportunity matching and SASL are proposed capabilities.

The six generated boards communicate visual direction. Incidental generated names, dates, email addresses, UI language availability and privacy statements are not requirements or evidence. In particular, no provider retention/training promise or isiZulu/Setswana voice availability can be inferred from a generated picture. This text and the clickable screen contract take precedence.

No browser observation was performed: the prior denial remains respected. Structural checks cover local rendering and route/asset consistency; they do not establish visual, accessibility, phone, voice or release acceptance. No production code, cloud resource, private document or public deployment was changed by this package.

The precise vector logo master and final custom wordmark are still a separate production task. The preview mark is a clean reconstruction for layout; the supplied selected reference is the visual authority. It must not be represented as a final traced/trademark-cleared master.
