# KAIRO Rain speech and interaction blueprint

**Research date:** 22 October 2026  
**Status:** planning evidence, not implementation or provider acceptance  
**Pilot scope:** adult learners (18+) confirmed by the user.  
**Decision:** keep the browser lesson usable by text/keyboard and low-data mode; use a managed speech path for the first interactive pilot; make language support capability-specific; treat SASL as a separately authored and Deaf-reviewed product path.

This note covers the selected KAIRO Access Lecture Theatre and Rain teacher. It is not a generic voice-agent design. Each recommendation below is tied either to the checked Rain runtime or a current provider/model source. “Listed” means the provider documents a feature; “validated” would require a KAIRO test with native speakers and representative devices. No language other than the current three English sample voices is validated end-to-end in Rain.

## Decision in one page

1. **First pilot:** use the existing KAIRO Google project only after an owner refreshes current billing/credit/quota and verifies API availability. Google STT V2 offers documented `zu-ZA` Chirp 3 in selected regions and `tn-Latn-ZA` `long`/`short` models in EU/US locations; only Zulu has a Chirp 3 row. Google TTS Chirp 3 HD has strong streaming behavior and a published price, but the current voice index yielded no confirmed South African English, isiZulu or Setswana voice. Do not make it the local-language narrator without an exact voice entry.
2. **For isiZulu narration and event timing:** Azure Speech documents isiZulu STT and two neural TTS voices (`zu-ZA-ThandoNeural`, `zu-ZA-ThembaNeural`). Azure's viseme table lists `en-ZA` but not `zu-ZA`. Its synthesis SDK exposes word-boundary and viseme events, but supported event availability varies by locale/voice. Use it as an isiZulu TTS candidate; test actual SDK events before mapping exact word actions. Azure for Students F0 state in the setup note is historical, not a verified current entitlement.
3. **For Setswana:** Google STT is a stronger listed candidate than the open model for an initial speech-input test; no official-cloud Setswana TTS voice was confirmed. `Hydramus/Simba-TTS-tsn-onnx` is a useful local/offline experiment, but its 109 MB browser payload, mobile performance, pronunciation and line-quality are untested. `UBC-NLP/Simba-TTS-tsn` is an alternative model reference. Neither substitutes for native-speaker review.
4. **Lip-sync and authored actions:** the Rain rig already accepts Rhubarb viseme timings (`A`–`H`/`X`) and has three exact-audio preanalysed samples. Live narration currently falls back to audio energy without timings. A viseme timeline is mouth-shape timing, not a word alignment. The feature “highlight the exact spoken word, look/point to it, write it on the board” needs a separate word-boundary timeline plus authored target/action anchors. Provider timing must be verified for the chosen locale; audio-clock alignment and cancellation must be generation-safe.
5. **Turn-taking:** implement an interrupt state machine in the app boundary, reusing Rain's existing exactly-once cue terminal contract. Provide push-to-talk and visible “I’m stuck” / stop buttons as deterministic paths; optional VAD may start cancellation at speech onset. Do not make VAD the only way to interrupt. A listening nod is an animation cue; never infer learner comprehension from it.
6. **SASL:** do not translate a text string into Rain's existing teaching hand gestures. SASL has its own grammar, spatial and non-manual components. The user requires authored, Deaf-reviewed signing; no general-purpose open, commercially cleared SASL signing model/corpus was verified in this research. Start with a separately authored human-signed glossary/lesson clip and Deaf-led review/consent. Any future generated signing needs separate evidence and authorization.

## What exists in Rain today

The current evidence is [CHARACTER-002 verification](../../character/verification.md), [Rain README](../../character/README.md), and its current [handoff](../../../coordination/handoffs/claude-character.md):

- GLB is 3,424,844 bytes; rig 77 joints, 31 facial shapes, 30 hand correctives, five clips; 229,366 triangles.
- The audio interface exposes `AudioInput.visemes?: Viseme[]`; each item is `{at, shape, weight}` and Rhubarb shapes A–H/X. Three included sample audio files have exact preanalysed timings. **No general live word-boundary or phoneme stream is integrated.** Without supplied timings, the live mouth uses amplitude fallback.
- The lesson/cue runtime has an exactly-once terminal event, and the browser test verified interruption: old cue terminal `interrupted`, replacement completes, no duplicate acceptance/terminal. This is a useful foundation, not proof of provider-stream cancellation, stale network response handling or learner mic turn-taking.
- 38 character browser checks passed. On one Intel UHD laptop in muted headless Edge: 22.5 median fps face-camera speaking, 3.4 MB asset; phones have not been measured. Startup in two headless runs was about 4–7 seconds; prefetching audio and timings was identified as a path to reduce fetch delay. These observations do not predict phone or network performance.
- Gaze/point/writing tied to exact spoken words, “tap number,” “I’m stuck,” listening nods, low-data voice selection, and SASL remain product requirements/planning—not delivered behaviors. Current hands make teaching gestures, not signs.

## Recommended architecture

Use the existing KAIRO local service boundary as an adapter point. Keep provider credentials on the server; browser asks for a short-lived lesson utterance/session, not API keys. Use one learner session at a time for the initial adult pilot. LiveKit is optional at later scale; its hosted media infrastructure is not necessary for one local browser prototype.

### Lesson authoring and speech cache

1. Retain canonical source text and provenance. Segment to authored sentences/paragraphs with stable `lessonId`, `segmentId`, source range and language. Human-review translations as separate text artifacts; do not overwrite source or silently substitute a different language.
2. Use pre-generated TTS by selected locale/voice for authored lesson content. Store audio and event metadata with a content hash + language/voice/model version. Prefetch the current and next small chunk on Play, not the whole textbook. Keep cache private/local and time-bounded unless learner consents to a longer save. Do not store mic audio by default.
3. Keep the learner experience usable when cloud consent is declined or network is poor: visible transcript, keyboard/text question entry, pause/resume, caption toggle, “I’m stuck” button, 2D lesson alternative and explicit low-data mode. Show model size before optional download (Simba ONNX card says roughly 109 MB). Do not surprise-download speech weights.

### Word, mouth and action timeline

Use a unified client-readable event shape, pending separate engineering ownership before implementation:

```ts
type LessonCue = {
  cueId: string;
  segmentId: string;
  startMs: number;       // relative to the exact audio asset's playback clock
  endMs?: number;
  textRange?: { start: number; end: number };
  action: 'highlight' | 'gaze' | 'point' | 'write' | 'nod' | 'listen';
  targetId?: string;     // allowlisted board/object anchor, never arbitrary generated target
  payload?: { text?: string; number?: string };
};
```

Keep provider `WordBoundary` (text offsets, start/duration) and provider `VisemeReceived` (timestamp/ID) as distinct event streams. Convert provider visemes to the Rain A–H/X map with a tested adapter. For compatible Azure English voice, SDK events may provide both word and viseme cues; for Zulu, the locale viseme list does not establish that support. Google Chirp 3 streaming provides streamed audio but does not advertise word-boundary/viseme events. Google Chirp HD supports SSML only for synchronous synthesis and only a subset in Preview; SSML tags are not supported on streaming requests. Do not promise `<mark>` action anchors for the streaming path. Synchronous selected-tag support has changed across docs/voice families, so verify the exact API and voice. [Chirp HD docs](https://docs.cloud.google.com/text-to-speech/docs/chirp3-hd), [Google SSML docs](https://docs.cloud.google.com/text-to-speech/docs/ssml), [Azure synthesis events](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis), [Azure viseme events](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis-viseme).

If timing events are unavailable, synthesize bounded sentence clips and estimate visemes from the exact output audio (e.g. Rhubarb) after generation. Do not use an audio-energy envelope as exact lip sync. Post-hoc forced alignment can be tested, but support/accuracy for Tswana and isiZulu must be measured; sentence clip duration alone is too coarse for exact word highlighting or board actions.

Tie word highlighting to the audio element's playback clock, not wall-clock timers. Authored action events reference allowlisted lesson anchors. For tap-number, the interaction should focus/select the existing numbered item, then invoke a grounded short explanation, point cue and possibly write cue for that same number. No free-form LLM scene coordinate/action output.

### Interruptible turns and “I’m stuck”

```text
idle → narrating → interrupting → listening → transcribing → answering → speaking → idle
                   ↘ paused / text fallback
```

- Visible Stop and “I’m stuck” button are immediate deterministic controls; push-to-talk starts listening on an explicit press. Optional browser VAD may stop audio on speech onset, then confirm turn with silence/end-of-utterance. User may disable mic/VAD.
- On interruption: abort TTS request, stop/flush queued audio, cancel current cue timeline, terminate the active lesson cue once as `interrupted`, retire a monotonically increasing generation/session token, and ignore any late chunk/callback for the stale token. Preserve last *completed spoken word/source span*, not unspoken generated text. Rain cue ledger already provides an exactly-once terminal-event precedent, but this full network/audio contract is future work.
- STT partial text is provisional; only final text enters the answer turn. Let learner edit transcript. Do not auto-submit a low-confidence/ambiguous recognition. For internet loss, degrade to text/keyboard or predownloaded captions; don’t silently send audio to another cloud.
- `I’m stuck` asks a source-grounded short re-explanation and offers one alternate form (worked example, simpler wording, translated text or diagram). It can trigger a listening nod before response, and an optional “still stuck?” choice after. Nods indicate listening state, never understanding or assessment.
- Distinguish backchannel (“mm”, “yes”) from intent only after observed pilot data. If VAD false-interrupts frequently, default to button/press-to-talk or adjust endpointing after measurement; do not hide a microphone-open state.

### Privacy, security and low-data constraints

- Text/audio transmission requires a clear affirmative cloud-speech choice and provider notice; retain no mic audio/transcript unless separately opted-in for progress or evaluation. Keep secrets server-side. Apply short retention/deletion policy and telemetry opt-out.
- Prefer sending compressed mono audio in short turns; avoid continuous ambient capture. Show estimated data usage before a first speech session and per session later. In low-data mode default to transcript/text and no autoplay; user initiates any voice asset fetch.
- Keep access controls and request length/rate limits at the service boundary. Account credit is not a budget. Cloud budgets/quotas and app-side hard request/character/minute caps should act together.
- The product pilot is adult-only (18+). No child-account handling is defined in this speech plan.

## Acceptance gates before implementation can be called a working pilot

Implementation should proceed only after an owner approves the interface and resolves the model/account choices. These are acceptance gates, not promised outcomes:

1. **Provider smoke matrix:** exact API version, region, locale, chosen voice/model, supported call mode, audio format, latency, cancellation, event availability and measured rate. Verify Google Chirp 3 Preview region and Azure F0 quota. No assumptions based on an account snapshot.
2. **Native-speaker quality:** native isiZulu and Setswana reviewers, including code-switching and subject vocabulary, review consented held-out speech; report WER/CER by speaker, noise/mic, accent and code-switch group, plus false accept/false interruption. Log error taxonomy and confidence; don’t optimize only aggregate WER.
3. **TTS reviewer set:** same meaning and pronunciation across short explanation, technical terms/names, numbers/formulae and code-switch. Blind native-listener ratings for intelligibility/naturalness and “would use in a lesson”; test word timing, phoneme/viseme mapping where provided. Capture exact voice/model/version and review consent.
4. **Alignment and stage cues:** compare event offsets to human annotations. Define tolerances with reviewers before scoring. Check word highlight changes at the right spoken word; point, gaze and board writing target the correct allowlisted anchor; tapping a number produces its own explanation; interruption does not show/write content the learner did not hear.
5. **Interrupt race test:** slow stream, rapid speech onset, silence, “I’m stuck”, repeated stop, network drop, late TTS chunks, stale events and restart. Exactly one terminal cue event; no old cue resumes; last-spoken source span survives.
6. **Phone and low data:** at least one representative low/mid-range Android phone, one older/low-memory device, throttled mobile data and offline. Report startup, P50/P95 first-audio latency, dropout, bytes/turn, CPU/memory/battery, frame rate with Rain; compare to reading/2D fallback. Current laptop-only character results do not satisfy this gate.
7. **SASL track:** Deaf-led requirements and funding, signed scope/content list, qualified native Deaf SASL signers, consent and ownership terms, linguistic review including facial/nonmanual markers, independent learner testing and update/withdrawal plan. Never gate core lesson access on generated signing.
8. **Spend gate:** confirm live credits and quotas through read-only account metadata, then run first bounded engineering experiments within the proposed $30 gross cap already authorized by the parent task owner; set alerts and app hard limits. If entitlement is unclear, do zero paid processing; if scope exceeds $30 or changes account/subscription, stop for revised authorization.
