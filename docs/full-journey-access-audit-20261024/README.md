# KAIRO Access: implemented capability and remaining ambition

**Audit date:** 24 October 2026. **Scope:** read-only repository source plus current dated release/handoff evidence. **Criteria:** Product, Usability, Sustainability, Intelligence and Impact. **Need:** accurately distinguish the current end-to-end learner path from the broader multilingual, multimodal, SASL and model-routing vision. **Acceptance:** identify real configured providers and limits; separate implemented code, tested API behavior, human/device acceptance and future work. No credentials, cloud account, browser, user data or secret file was inspected; no cloud commands/calls were made.

## Status in one paragraph

KAIRO Access has a real but bounded account → upload/paste → extraction review → cited/editable lesson → text or narrated teaching → prepared activity/practice → saved evidence/resume path. Hosted synthesis and speech use Google only: the default Gemini 3.5 Flash-Lite model through the Vertex AI `global` `generateContent` endpoint, plus consented Google Chirp 3 HD speech. Firebase Auth, owner-scoped Firestore and private Cloud Storage back the account workflow; Cloud Tasks dispatches imports. Text/document parsing and limited OCR are implemented. A selected-passage translation draft is available in English, Afrikaans, isiZulu, isiXhosa, Sesotho or Setswana. Browser/device speech is another route. The local camera feature tracks hand landmarks; it is not a SASL translator. The current hosted service is IAM-private, and the latest release evidence records revision `kairo-app-00006-885` with 100% traffic and 18/18 synthetic API checks; that does not make it externally accessible or establish browser/device acceptance.

## What needs to be built or accepted before matching the full vision

1. **Access decision:** resolve a judge-appropriate login path; current IAM-private deployment is not publicly reachable by design. No workaround for the denied public IAM step is implied.
2. **Human journey acceptance:** authorized reviewers should complete source → correction → cited lesson → KAIRO/reading → relevant practice → evidence → resume using the current account, then report errors. Root release evidence expressly lacks browser/device and assistive-tech acceptance.
3. **Language quality:** native/fluent reviewers assess each supported translation pair and technical domain; improve language selection in the studio companion and distinguish read-aloud text from synchronized captions. Keep untranslated source/reading fallback.
4. **Multimodal ingestion:** for one justified target (e.g. diagrams/formula pages), design a separate reviewed pipeline with page-level provenance, model/rights/privacy review, extraction confidence and human correction. No full multimodal promise follows from current OCR.
5. **Voice/STT:** first decide whether speech input is a validated learner need. Add microphone/STT only after consent, data-region, retention and accessibility review; preserve text input. Expand voice language only after vendor coverage and fluent-speaker/device acceptance.
6. **SASL:** co-design with Deaf SASL educators/signers and rights holders, define a bounded target and licensing/consent, collect/evaluate signer-disjoint data, and fund fluent Deaf review. Until then call current feature hand-landmark tracking only; keep signed-learning resource link and text/keyboard/caption alternatives.
7. **Reliability, security and scale:** close release residuals in the security handoff (deletion/retention, incident/support operations, distributed limits, runtime/Python/base-image inventory and scan, cost reconciliation, actual auth/cap settings). Current single-pilot configuration and app quotas are not a billing hard stop.
8. **Impact/intelligence evidence:** test an approved learning task and compare source accuracy, practice quality, time/help and delayed transfer against a baseline. Use consented diverse users; report sample size and uncertainty. No AI model, translation or simulation should be described as improving outcomes before this is measured.
