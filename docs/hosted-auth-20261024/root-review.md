# Independent hosted-core review

**Reviewer:** `codex-hosted-auth-20261024-a` — Codex, gpt-6.1-sol, effort unknown  
**Scope:** Read-only review of `studio/server/hosted-core/{firestore,firebase-verifier,app,entry}.mjs` and `studio/tests/hosted-core.test.mjs`.  
**Judging criteria:** Product and Usability (private persistence and credible saved state); Sustainability (hosted service failure boundaries); Intelligence (identity and persisted evidence are represented accurately).

## Findings

1. **P2 — Origin restriction silently disables when `KAIRO_ALLOWED_ORIGIN` is unset.** In [app.mjs](../../studio/server/hosted-core/app.mjs#L8), the origin is validated only when truthy; at lines 12–14 an incoming `Origin` is rejected only if it differs from `allowedOrigin`. With undefined configuration, any supplied origin passes this check. The check also does not emit CORS response headers, so it is not an effective browser CORS allowlist. Bearer-token authentication still gates the routes, so this is not by itself an authentication bypass. Fail startup when the required origin is absent, or implement an explicit allowlist and matching CORS preflight/response behavior. Current `entry.mjs` passes the environment value directly at line 10. No runtime config evidence was available in the reviewed workspace, so whether the deployed revision is configured remains unverified.

2. **P2 — Revoked Firebase ID tokens remain accepted until normal JWT expiry.** [firebase-verifier.mjs](../../studio/server/hosted-core/firebase-verifier.mjs#L28-L31) verifies signature and standard claims, then returns the UID without a revocation/disabled-account check. There is no `checkRevoked` equivalent. A copied bearer token can therefore continue to access hosted progress until expiration after sign-out, account disablement, or refresh-token revocation. Decide whether this risk fits the short-lived progress foundation; otherwise add revocation checking through a trusted verifier and test revoked/disabled identities. The current synthetic RSA tests (lines 88–102) cover signature, expiry, audience and auth time but not revocation.

3. **P2 — Existing tests do not prove the actual entrypoint wires cryptographic verification.** `entry.mjs` composes the real verifier and repository at lines 5–10, but the route test [hosted-core.test.mjs](../../studio/tests/hosted-core.test.mjs#L70-L86) injects a verifier that treats any bearer text as a UID. The RSA test at lines 88–102 tests `createFirebaseVerifier` in isolation. These are useful unit checks but leave the production composition untested. Add a composition-level test around a factored factory or launch the entry with injected cert/auth dependencies and synthetic signed tokens; preserve the clear boundary that this is synthetic cryptographic integration evidence, not real-user login acceptance.

4. **P2 — Browser client integration is incomplete if the hosted service is a separate origin.** [app.mjs](../../studio/server/hosted-core/app.mjs#L12-L14) checks `Origin` but does not set `Access-Control-Allow-Origin`, `Access-Control-Allow-Headers: Authorization, Content-Type`, `Access-Control-Allow-Methods`, or handle `OPTIONS`. A browser frontend hosted on a different origin cannot make/read authenticated API requests even when its origin matches `allowedOrigin`; preflight fails. If the intended client is same-origin or server-to-server this may be acceptable, but that route must be documented and tested. Otherwise add narrowly scoped CORS and test allowed/disallowed origins and preflight. This is a usability/integration blocker, not a token bypass.

## Reviewed areas without a confirmed defect

- **Cross-owner path:** [firestore.mjs](../../studio/server/hosted-core/firestore.mjs#L13-L18) derives document paths from the supplied UID hash and checks path, owner, kind and ID on reads. [app.mjs](../../studio/server/hosted-core/app.mjs#L17-L27) supplies only `req.kairoIdentity.uid` to get/put/remove. Client values (including an embedded `uid`) are persisted only inside that owner's payload and do not select the path. The in-memory repository and HTTP tests exercise equal IDs under two token-derived owners, but this is synthetic evidence rather than live Firestore cross-owner validation.
- **Forgery:** The verifier restricts `alg` to RS256 and `kid` to a fetched public-certificate key, uses Google's JWT signature verifier, pins audience/issuer and checks expiry. The included synthetic RSA test rejects wrong-key, wrong-audience and expired tokens. No forged-token acceptance was apparent by inspection. Actual Firebase signer/account behavior is unverified.
- **CAS:** Writes and deletes use Firestore `currentDocument.exists=false` or update-time preconditions; stale preconditions map to 409. Review found no obvious last-write-wins path. Tests model these semantics in memory; deployed Firestore concurrency has not been evidenced here.
- **Route scope:** Hosted app mounts only health and `/api/hosted` identity/progress routes and ends with 404; no global local workspace routes are mounted. This is appropriately narrow for the initial progress foundation. The public health route is minimal and Cloud Run's reported private IAM boundary is assumed from the parent task, not independently verified here.
- **Runtime/deploy:** `entry.mjs` uses `PORT`, binds `0.0.0.0`, uses Google Application Default Credentials and makes a bounded Firestore startup read before listening. I found no deployment manifest or recorded deployment evidence in the requested review scope, so container entrypoint, dependency inclusion, service account binding, IAM ingress, and the claimed startup-readiness revision are not independently confirmed by this review.
