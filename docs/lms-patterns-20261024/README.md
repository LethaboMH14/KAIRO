# LMS and task-state patterns for KAIRO

**Checked:** 2026-10-24
**Scope:** Official-source comparison for learner navigation, progress, lesson editing, assessment feedback, recovery, accessibility and learner/instructor boundaries. Source-only review of KAIRO code; no runtime changes or in-app observation.
**Judging:** Product, Usability and Intelligence.
**Learner need:** Find relevant material, see a trustworthy next action, understand where a lesson came from, recover from interruptions, and know what counts as saved or assessed.

This memo compares documented interaction patterns, not brands, visual designs, quality rankings or feature parity. Learner feelings are design hypotheses until tested with KAIRO learners.

## Executive recommendation

Use a small, learner-readable workflow status model across the source-to-evidence path:

- **Not started** — no action recorded.
- **In progress** — the current activity can continue.
- **Ready to check** — extraction or a response needs the learner’s review.
- **Saved in this browser** — a local browser record was successfully written.
- **Needs attention** — a read/save/source/revision problem needs a choice.
- **Try again** — a specific retriable action is available.

Keep “complete” for an explicitly completed activity, not a learner’s overall competence. Do not introduce LMS-style grades, mastery percentages, teacher sign-off, course certificates, or required sequencing unless KAIRO adds those actual contracts and evidence.

Keep the existing plain learner flow: **Choose material → Check source → Shape lesson → Learn → Practise → Keep my work → Resume**. Make each step’s immediate action and save boundary visible. Use a single, short next-step sentence and keep a reading alternative available when 3D, voice, extraction or a service fails.

### Account and role boundary

The account form component exists at studio/src/account-ui/AccountPanel.tsx, but current source search finds no route/component mount. Hosted backend research demonstrates owner-scoped progress API behavior, not a fully connected learner account. Sources, revisions, lesson history and browser data have not migrated into the hosted account store. Keep sign-in/account transfer out of the current pathway acceptance until the integration owner connects it.

The teacher identity in KAIRO is **KAIRO**. LMS references use “teacher” for human instructors who set course requirements, view reports or return assessments. KAIRO’s present product does not offer a human instructor gradebook or authority to mark learner work complete. Maintain the distinction in labels, privacy copy and data model; keep practice evidence self-reported/unverified where appropriate.

## Copy proposals (plain text, C identity unchanged)

These are proposals, not observed usability results or approved production copy.

- **Empty material:** “Start with a course file, a passage, or the guided example. You can check the extracted words before making a lesson.” Actions: “Choose material” and “Try the guided example.”
- **Partial extraction:** “We found text in 4 sections. 2 more sections need a separate check. Review what was found before continuing.” Actions: “Review extracted text” and “Keep this source for later.”
- **Cloud lesson consent:** “Send up to 12,000 reviewed characters selected for this goal to Google Cloud to create the cited lesson. Your reviewed source remains in this local workspace. The uploaded original is kept only if you choose its separate retention option.” Any actual host/provider disclosure must reflect current runtime configuration.
- **Generation failure:** “The lesson could not be created. Your reviewed source and goal are still here.” Actions: “Try again” and “Make a local reading lesson.” Only say “still here” after confirming the state is retained.
- **Saved draft conflict:** “Another tab has a newer saved version. Your changes are still here. Export them before loading that version.” Actions: “Export draft” and “Load saved version.”
- **Saved place unavailable:** “Your last place could not be read. Earlier saved work was left unchanged. Continue from the first chapter or return to My material.”
- **Account boundary:** “Your lesson and source history are not in your account yet. This local preview keeps sources in the app workspace and study notes in this browser.” Only display if the backend/client state remains as currently documented; update when integration changes.
- **Evidence label:** “Practice record · saved in this browser · self-reported, not an official mark.” For in-memory evidence: “This run is not saved. Export it before leaving if you want a copy.”

Avoid generic “Something went wrong,” unlabeled spinners, “100% complete,” “mastered,” “teacher approved,” “synced” and “saved to your account” unless each claim maps to a real, tested state.

## Smallest acceptance plan

Each check is proposed, not executed in this source-only package.

1. **First-use route:** fixture with no material; verify obvious example/choose actions, then a reviewed source leads to a lesson with a visible original locator and reading alternative.
2. **Partial file:** synthetic mixed native/empty/scan fixture; verify coverage names omitted/unknown units, review and AI consent remain separate, and the user can continue with available text.
3. **Goal selection:** late relevant source phrase beyond 12k; verify correct goal-ranked quote, source locator/offset and stale-revision rejection. Verify current language does not claim the whole 48k review was sent or semantically searched.
4. **Draft state:** edit/save/undo/import/export and two-tab conflict; verify the current saved version and unsaved user draft both remain recoverable, with no silent overwrite.
5. **Question feedback:** wrong answer reveals exact supporting passage and a retry; next suggestion cites the related recorded attempt and is still described as a practice rule, not ability level.
6. **Resume:** reload with saved, absent, corrupt, stale and conflicting state; verify reading-first fallback, explicit status and preserved earlier record. Separately test source workspace unavailable vs browser-local reading data.
7. **Account transition:** after account mount only, test sign-out/account-switch/reload/two account isolation, record scope and opt-in migration; no current account-sync acceptance.
8. **Accessibility and device follow-up:** later human/device check keyboard sequence, skip link, focus visibility, status announcements, zoom/reflow, reduced motion and phone/low-bandwidth fallback. Source attributes alone do not certify accessibility.

## Judging and gaps

- **Product:** A source-backed path from actual material through an authored lesson, practice and resume is more relevant than a generic course dashboard. Acceptance needs exact reviewed-source identity and recovery state through the path.
- **Usability:** Clear step names, one next action per failure, plain save scope and editable drafts can reduce “what now?” uncertainty. These are design hypotheses pending learner checks.
- **Intelligence:** Goal-ranked lexical selection, exact citations and feedback tied to a practice attempt make the system’s scope inspectable. Citations do not prove factual correctness or claim entailment.
- **Remaining judging evidence:** Creativity and Presentation need a coherent live demonstration; Sustainability needs measured costs/limits; Impact needs learner/user validation and outcomes. This research does not establish any of them.

No browser/device sessions, screenshots, private learner records, tests, builds, cloud calls, code changes or deployment were made by this lane. Parent integration and human learner evaluation remain required.
