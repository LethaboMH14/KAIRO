### Illustrative Cloud Run arithmetic

Using the public Cloud Run default USD price table as checked on 24 October 2026 (not a region quote): L4 non-zonal GPU `0.0001867 USD/s` + 4 vCPU at `0.000018 USD/vCPU-s` + 16 GiB at `0.000002 USD/GiB-s` = `0.0002907 USD/s`. The minimum L4 CPU/memory sizes come from the GPU docs. The pricing page rounds usage to the nearest 100 ms. A 15-minute running window gives about `$0.26163` at those displayed rates; 18×24 hours gives about `$452.11`. This excludes other SKUs and regional price differences and is not a forecast or a credit-balance statement. If future regional rates differ, recalculate from the selected region's exact SKUs before deployment. [Cloud Run GPU](https://docs.cloud.google.com/run/docs/configuring/services/gpu), [Cloud Run pricing](https://cloud.google.com/run/pricing)

## Three bounded experiment proposals — not executed

All three require an owner to authorize execution later. Use synthetic/public inputs only; never put private learner material into a remote GPU or public search prompt without explicit data-region and privacy review. These are source-grounded proposals, not completed experiments.

### 1. Managed Vertex baseline — recommended first

- Keep the current managed `gemini-3.5-flash-lite` path and `global` location; no endpoint deployment, GPU, Search grounding, or route change.
- At most 20 synthetic prompts, each capped at 2,000 input tokens and 256 output tokens; one request at a time; no automatic retries.
- Token maximum: 40,000 input and 5,120 output. At current published global standard rates of `$0.30/M` input and `$2.50/M` output, list estimate is `$0.0248` (40,000×0.30/1M + 5,120×2.50/1M). Reprice before use if the model, location, price date or limits differ. [Agent Platform pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)
- Stop after 20 requests or immediately on an unexpected response/schema, token-limit mismatch, or any request error. Before execution, owner must check the actual project spend and eligible spend-cap state; do not treat an alert as the stop condition. No live call was made.

### 2. Public-source retrieval and grounding — cost cannot be bounded by prompt count alone

- Candidate: current managed Gemini 3.5 Flash-Lite with Google Search grounding, using at most five sequential public/non-sensitive synthetic questions; one call in flight, 256 output tokens per question; no retry.
- Inspect each response's grounding metadata and count actual `webSearchQueries`/Grounding Queries, source URLs and source fit. The five-prompt limit is **not** a hard query-cost ceiling because one prompt can fan out to multiple queries. Current Gemini 3 grounding cost after monthly 5,000-query aggregate is `$14/1,000` actual queries, plus model token usage; formula after free residual `R` is `max(0,Q-R) × $0.014 + input_tokens×input_rate/1M + output_tokens×output_rate/1M`. The exact remaining monthly query allowance is unknown. [Agent Platform pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)
- Gate: do not execute until the owner verifies the project/service, current remaining included queries, an eligible project+Agent Platform spend cap set below their approved limit, and that this grounding surface exposes/counts actual query metadata. The cap is not instantaneous and does not eliminate in-flight overage. Stop after five prompts, on any unsafe/irrelevant source or unexpected fan-out, and at the pre-approved cap. If those gates are unavailable, hold this experiment. No bulk scraping or copying protected material; preserve original source links and rights review.

### 3. Cloud Run L4 feasibility — dry-run only; deployment deferred

- Johannesburg has no documented Cloud Run L4 region. A future synthetic/public-data proof would need a supported region such as `europe-west1` (Belgium) or `europe-west4` (Netherlands), owner approval for cross-region data handling, verified quota/capacity, and a compatible container/model serving path. It must remain IAM-private.
- If ever authorized: one service, `max instances=1`, `min instances=0`, 4 vCPU/16 GiB minimum, no zonal redundancy, one concurrency, at most 10 synthetic prompts, and a manually enforced 15-minute elapsed test window; then stop and delete the service. Weights/download/boot time are inside the billed lifecycle. GPU docs' ~5 seconds covers GPU host readiness only, not model loading.
- Cost ceiling proposal: do not deploy unless exact selected-region price is checked and estimated spend is under `$0.50`. At the displayed default non-zonal formula (`0.0002907 USD/s` including minimum CPU/RAM), 15 minutes is approximately `$0.26163`, before storage/network/logs/artifacts. Formula: `billed_seconds × (p_L4 + 4×p_CPU + 16×p_RAM) + storage + egress + logs + artifacts`. Stop/delete at 15 minutes or immediately if the service fails to reach zero after the test. The stated cap is only a proposed test ceiling; no cap or service was configured. ## Integration recommendations

1. Keep KAIRO's current managed Vertex model for its existing hosted requests until token and quality measurements justify a specific change. Managed API cost is per token; a self-deployed Model Garden model introduces endpoint-machine lifecycle and quota costs.
2. Keep deterministic motor calculations in tested application logic. An LLM may help explain authored/source-supported steps, but does not replace numerical validation.
3. Add public web grounding only for public, bounded questions where visible sources can be reviewed. Log the actual grounding queries and source URLs; do not call a broad prompt count a query cap. Keep private learner records and private course files out of public search inputs.
4. Defer GPU hosting until a measured workload needs it. The L4 is unavailable in the current Johannesburg Cloud Run region, and a supported region means cross-region processing that needs owner/privacy review. Ollama Cloud is also hosted primarily in the US with possible Europe routing, per vendor; do not assume it provides South African data residency. Model Garden self-deployment is a separate serving project, not a free way to host arbitrary weights.
5. If a cost control is needed, have the owner inspect project/service scope and configure an eligible spend cap deliberately, with a margin for latency and fixed resources. Keep alerts for visibility; they do not stop spend. This review did not inspect or change billing configuration.
