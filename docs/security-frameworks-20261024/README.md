# KAIRO security framework map and quantum readiness

**Research date:** 24 October 2026. **Scope:** source review and primary-source research only; no active scanning, browser observation, cloud inspection, secret access, dependency installation, or runtime edits. This is an engineering backlog, not a compliance assessment, penetration-test report, or claim of quantum-safe operation.

## Why this work matters

KAIRO handles private learner uploads and derived lessons, then may send reviewed excerpts to a model after consent. Security preserves the learner's private study material and makes the source → review → lesson → practice → evidence → resume path trustworthy. This supports Product (private, dependable learner journey), Usability (clear consent and failure recovery), Sustainability (bounded resource use and defensible operations), and Intelligence (source-grounded processing that cannot turn uploaded instructions into authority).

### Minimal SSDLC adoption

Use [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) as the lifecycle vocabulary: document security requirements and threat assumptions; keep source/dependency provenance; use least-privilege build/deploy identities; test the real authorization and data paths; record findings and risk owners; preserve review and rollback evidence. Use [NIST SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final) alongside it for the GenAI-specific lifecycle. Use [OWASP ASVS 5.0.0](https://asvs.owasp.org/) as the versioned control verification catalogue, not a badge. Use [OWASP API Security Top 10 2023](https://owasp.org/www-project-api-security/) for API risk framing; use [OWASP GenAI/LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) for model-boundary risks. Each is guidance; completing a mapped subset does not establish certification or comprehensive security.

Keep the practical security acceptance gate attached to the learner journey: (1) prove unauthorized owner access fails; (2) uploaded bytes/text cannot change authorization or create tools; (3) source quote/revision stays attached to generation and saved work; (4) cancellation, parser/provider failures and quota exhaustion preserve prior work; (5) deletion and retention semantics are testable; (6) reviewer ingress remains deliberately private until explicitly approved.

## MITRE: use ATT&CK and ATLAS for different questions

[MITRE ATT&CK](https://attack.mitre.org/) catalogs adversary tactics and techniques based on real-world observations, mainly for enterprise/mobile environments. Use it to structure infrastructure/account scenarios such as credential access, valid-account use, session theft, collection, exfiltration, and impact; it is not a vulnerability checklist and a mapped technique does not prove exploitability.

[MITRE ATLAS](https://atlas.mitre.org/) is the AI-focused living knowledge base, including attacks on AI systems, abuse/manipulation of AI capabilities and AI-enabled harmful behavior. For KAIRO, prioritize direct/indirect prompt injection, poisoned study files, sensitive-data exfiltration through model output/rendering, and resource abuse. ATLAS complements OWASP LLM threats; it does not replace conventional API authorization and cloud identity testing. Current model calls have no inspected agent tools or arbitrary retrieval, so do not map hypothetical agent tool abuse as an implemented exposure.

## Quantum readiness recommendation

**Recommendation: inventory and track provider transition; do not add application-level PQC now and do not call KAIRO quantum-proof/quantum-safe.** The inspected app delegates TLS, identity, database/storage encryption and managed signing to Google/Firebase services. There is no evidence that KAIRO itself holds long-lived asymmetric ciphertext or private signing keys. The current app has no customer-managed KMS key configured in the inspected code/docs; Google default storage encryption is provider-managed. A fresh configuration review is required to validate this deployment-specific statement.

Risk is primarily long-lived confidentiality exposure: a captured TLS session encrypted with classical public-key exchange could be stored and decrypted in a future capable quantum setting (harvest/store now, decrypt later). Prioritize any learner records whose confidentiality must last beyond the provider's migration horizon. Google documentation says Cloud Run frontend terminates TLS and forwards to the container over an encrypted channel; Google has described ML-KEM (FIPS 203) for Google Cloud network encryption on Google and selected native services, while its published roadmap describes migration of public-facing services to PQC by 2029. These provider-wide statements do **not** prove the exact current Cloud Run ingress, every Firebase/Vertex/API hop, every region, or all stored-data key wrapping used by this deployment. Obtain service/region-specific provider evidence before a high-assurance claim.

NIST has standardized [FIPS 203 ML-KEM](https://csrc.nist.gov/pubs/fips/203/final) for key establishment, [FIPS 204 ML-DSA](https://csrc.nist.gov/pubs/fips/204/final) and [FIPS 205 SLH-DSA](https://csrc.nist.gov/pubs/fips/205/final) for signatures. These are standards to plan around, not drop-in app toggles. Google says its default at-rest storage uses AES-256 and notes symmetric AES-128-and-later remains resistant to quantum attacks; PQC transition focus is asymmetric key establishment/signatures, not replacing AES with a homegrown scheme. Cloud KMS PQC capabilities and load-balancer-specific hybrid key exchange are product-specific and do not imply KAIRO has enabled them.

Practical staged plan:

1. Record a crypto inventory: Cloud Run edge TLS termination; Cloud Run-to-container channel; Firebase Auth token/session mechanisms; Firestore/GCS at-rest key management; Cloud Tasks OIDC; Google API auth; any signing or export verification. For each, record service, region, owner, algorithm/config evidence, data sensitivity/lifetime, vendor transition evidence and review date.
2. Ask Google/provider documentation or support to confirm Cloud Run `africa-south1`, Firebase Auth, Firestore, Storage and Vertex API transport and at-rest PQC transition scope; record unknowns. Do not enable CMEK/PQC options until cost, availability, recovery and region support are reviewed.
3. Revisit annually and before any long-retention/sensitive-data pilot, new self-managed TLS, local cryptographic library, institution integration or signing feature. Require crypto agility at those seams and migration/rollback tests.
4. Keep short-lived credentials, minimize source retention and make deletion work. These reduce the value of harvest-now data even while the provider migration proceeds.
