## Security Requirements (Risk Assessment)

KAIRO handles private study uploads, extracted text, reviewed source revisions, AI-generated lessons and learner working. Our security priorities are preventing another learner from accessing these records, protecting account sessions, preventing malicious documents or AI output from executing actions, and bounding processing costs. The current pilot uses fictional judge accounts and an IAM-private Google Cloud Run service. Private APIs require Firebase-verified sessions and server-derived owner identity; changing a course code, record ID or client field must not grant access to another account.

We use OWASP API Security Top 10 (2023), ASVS 5.0, OWASP LLM Top 10 (2025) and NIST SSDF as engineering references. We minimise model input, require explicit consent for cloud lesson/help/voice processing, and retain source citations and revision checks. Camera access is optional local hand tracking: no video recording or camera-frame upload is implemented; microphone permission is disabled. Residual risks include document-parser vulnerabilities, misleading model explanations, broad server permissions, account abuse, and incomplete end-to-end deletion/retention workflows. We do not claim POPIA certification, comprehensive OWASP compliance or quantum-safe operation.

## Threat Modelling & Design Review

We model the boundaries between learner browser, Firebase authentication, Cloud Run API, Firestore/GCS owner records, the import queue/parser and Google model/speech APIs. Main abuse cases are object-ID substitution, forged enrolment/progress, stolen or revoked sessions, cross-origin mutations, malicious uploads, prompt injection, fabricated citations and excessive resource use. MITRE ATT&CK informs account/infrastructure scenarios; MITRE ATLAS informs AI-specific scenarios. These mappings guide investigation rather than prove that an attack occurred.

The application derives ownership from a verified session, not submitted UID fields. Queue jobs require the expected service-account identity. User documents and goals are untrusted data; model output has no connected command/tool execution and is checked against the supplied source citations. We preserve learner work on version conflicts rather than silently overwrite it. Design review identified a login/recovery throttling gap: rotating emails bypassed the original pair-based limit. We reproduced and corrected it with independent account, client and process-wide budgets. Distributed throttling, stronger parser isolation, finer runtime permissions and application-level audit events remain planned hardening.

## Development (Secure coding practices)

The Node/Express and React application validates identifiers, request sizes, record sizes, source revisions and generated lesson structure. Firebase sessions use HttpOnly, Secure, SameSite=Strict cookies, recent authentication and revocation checks. State-changing requests require the configured same origin; provider failures use generic messages. The educational SQL trace uses bound parameters. Private records and blobs use owner-derived addresses, integrity metadata and version/precondition checks. Ordinary lesson text is rendered through React rather than executed as HTML. Retained originals receive fixed content types, nosniff and a restrictive sandbox policy.

Uploads use an extension/signature prefilter, an 8 MiB bound, parser time/output limits, archive-expansion bounds and temporary-file cleanup; malformed images must also pass the real decoder before extracted source pages exist. Source lesson/help and cloud speech routes require processing consent; cloud requests have usage allowances. The separate prepared CS question route is a deliberate cloud question action and still needs its consent UX reviewed. Camera models/workers are locally served and hash-checked. The runtime uses a dedicated attached identity and no user-managed service-account keys; its remaining broad roles are documented for reduction. Builds use npm's lockfile, a non-root container and an explicit staging allowlist that excludes credentials and private uploads. A production CycloneDX dependency inventory was generated; Python/base-image reproducibility and vulnerability scanning remain separate work.

## Security Testing

We ran bounded local attack-case tests against actual routers and validators using synthetic data, mocked identity/provider services and in-memory storage. Cases include email-rotation/forwarding-header abuse, per-account sign-in/recovery limits, expiry, foreign/missing origins, oversized/revoked cookies, cross-owner source/lesson/draft/job reads and mutations, protected enrolment/quota records, SQL attack strings, forged model citations/tool fields, malformed Office packages, oversized archive metadata and truncated images. The rate-limit defect failed before the fix and passed afterwards. The focused account/adversarial run passed 20/20; the extractor package passed 7/7. The final aggregate result is recorded in the accompanying release status.

The npm advisory check reported zero known findings at this scan date; this covers npm's advisory data, not unknown flaws or Python/OS/container packages. Read-only cloud checks confirmed private invocation, bucket public-access prevention and uniform access, zero user-managed runtime keys and resource caps. Existing live synthetic-account isolation checks are retained as API evidence. This is a scoped internal adversarial assessment, not an independent penetration-test certificate. No public load attack, third-party scan, real learner document test, live hostile-model red-team or browser/camera observation was performed.

## Assessment & Secure Integration

Security changes are registered, claimed, reviewed and handed off with executable evidence. Promotion retains private IAM access; a green build does not authorize public exposure. We track deployed revision, test results, dependency inventory, actual findings and unresolved risks. Uploaded instructions and model responses cannot approve permissions or trigger external submissions. Framework mappings, cryptographic inventory and a prioritised follow-up test plan accompany this SSDLC.

Before a wider pilot, we must complete distributed abuse controls, parser/service-account isolation, application audit/alerting, tested recovery and deletion/export semantics across queued jobs and backups, fresh Python/OS/image scans, provider retention review and human/device accessibility checks. Incident response will disable affected processing, revoke relevant sessions/credentials, preserve redacted evidence, assess impact and restore only a reviewed revision. For quantum readiness we inventory provider-managed TLS, token signatures and stored-data encryption, minimise long-lived sensitive data and follow NIST/Google migration guidance. We have not enabled or independently established post-quantum protection on every KAIRO connection.
