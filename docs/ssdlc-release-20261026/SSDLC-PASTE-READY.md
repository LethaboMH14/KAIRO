# KAIRO — SSDLC form text

Prepared 26 October 2026 for the five screenshot fields. Review before submitting. The framework names below describe engineering references, not compliance or certification.

## Security Requirements (Risk Assessment)

KAIRO processes learner-supplied study files and text, extracted and corrected source revisions, source-linked lessons, personal practice, and optional consented AI or voice requests. The main risks are cross-account disclosure or mutation, account/session abuse, malicious or misleading uploads, stale or fabricated citations, prompt injection, unauthorized provider processing, and resource exhaustion. Hosted private APIs derive the owner from a verified Firebase session; the multi-source lesson path checks every selected owner source and immutable revision before use and rechecks provenance on reads. The current hosted service is IAM-private. The loopback preview is a separate single-user store, not a multi-user security boundary.

We use OWASP API Security Top 10, ASVS, OWASP LLM Top 10 and NIST SSDF as review references. Risk reduction includes explicit cloud-processing consent, bounded uploads and model requests, owner/version checks, strict output validation, and source-readable alternatives. Residual risks include parser isolation, distributed abuse resistance, broad runtime permissions, provider-side retention, complete deletion/recovery, and unmeasured educational correctness. We do not claim legal compliance, certification, a comprehensive vulnerability finding, or quantum-safe operation.

## Threat Modelling & Design Review

We review the boundaries between learner device, IAM-protected Cloud Run, Firebase session verification, owner-scoped Firestore and Cloud Storage, Cloud Tasks and its OIDC-authenticated import worker, document parsers, and separately configured AI/speech providers. Abuse cases include object-ID substitution, revoked/stolen sessions, cross-origin writes, abusive login/recovery, crafted files and parser resource use, prompt injection, false citations, source revision changes during work, fallback to an unapproved provider, and excessive cost. Sign-in and recovery counters are held in a process-local map, so they are not a distributed abuse-control system.

The hosted routes require a verified session and same-origin state changes; the server supplies the UID to the owner repository. Writes use version preconditions. Multi-source requests allow one to eight distinct reviewed sources, bind their revisions into a bundle revision, retain exact quote offsets, and fail closed when a source changes. User documents and goals are treated as untrusted model input; output is schema/citation checked and has no command execution capability. Google, Groq, OpenRouter and the explicitly configured AIML adapter are allowlisted server-side. The existing CSP permits inline styles and selected blob/WASM sources; this policy was preserved during the font repair and needs continued review. MITRE ATT&CK and ATLAS inform scenarios only; no mapped coverage or certification is claimed. Remaining design work includes distributed rate limiting, parser/runtime isolation, end-to-end deletion/recovery, and operational audit/alerting.

## Development (Secure Coding Practices)

The hosted Express entry applies security headers and the existing Content Security Policy (`default-src 'self'`, explicit script/font/connect/object policies), disables `X-Powered-By`, checks exact allowed origins and requires the session guard before private workspace routes. The policy still permits inline styles and selected blob/WASM sources. Firebase session cookies are HttpOnly, SameSite=Strict and Secure in hosted mode; sessions are verified for revocation. Firestore record paths are derived from a hash of the authenticated UID, payload identity is checked when read, record sizes are bounded, and writes/deletes use version checks. Upload admission allows listed formats up to 8 MiB and checks binary signatures; extraction is bounded by time, output, page/section and reviewed-text limits, with temporary-file cleanup and cancellation paths.

Cloud lesson, passage, speech and multi-source operations require explicit consent. Provider IDs/models are selected from server configuration, fallback requires separate consent, request IDs are idempotent, durable usage reservations are bounded, cancellation is propagated, and citations/outputs are validated before persistence. The displayed content is rendered as text; no user-provided code or model-produced HTML is executed. Secrets are configured server-side and the deployment identity is used instead of committed service-account keys. On 26 October, the hosted font failure was corrected by removing an off-origin CSS import and using the existing bundled font; the Content Security Policy was not weakened.
