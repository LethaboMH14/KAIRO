This is prepared teaching/model content, not an externally validated physical motor.
- `studio/src/pump-lab/PumpLab.tsx`, `session.ts`, `readout.ts`, `report.ts`, and `studio-teaching-host/PumpHost.tsx` support a simulation workflow including predictions, readings, settings, cases, evidence reports, local save and contextual coaching. - `studio/src/learning-flow/StudioCompanion.tsx` calls `coachFor` from `studio/src/studio-coach/model`; it is deterministic authored coaching that receives selected part/task/readings context. It is not an LLM call or an evaluator of the learner's typed explanation. The four choices are Explain, Hint, Predict and Check; “Check” prompts the learner to reason but has no learner-answer input in this host.
- `StudioGuide.tsx` visibly retains `response.text` and `response.prompt`. Its label says “KAIRO text and captions.” `TeacherProvider.tsx` holds a `caption` value (whole utterance for device speech, chunks for cloud speech), but `StudioCompanion` does not pass that value into `StudioGuide`. The visible panel is useful readable text, but it is not synchronized word/phrase captioning of the active utterance. Do not describe this as timed captions or claim an active captions track. Also, `StudioCompanion` currently calls `teacher.say(..., 'en-ZA')` directly; its read action does not forward the user's selected `settings.language`, so a non-English installed voice preference may not affect this studio utterance.
- `AccessDialog.tsx` is opened on demand as a native modal, stops narration on entry, places focus on Close, and restores the prior focus on cleanup. Voice selection is separate from translation; the UI states that selecting a voice language does not translate English. Google voice is explicitly English, consent-gated, and device reading remains an alternative. Draft translation is reached from a selected source passage in the classroom.
- The dialog initially reveals camera controls without requesting a stream. `TrackingPanel` requests video only after the learner presses **Start camera**, explains local tracking and a stop control, and shows denial/no-camera/error recovery. `signing/contract.ts`, `lifecycle.ts` and `README.md` state this model finds hand landmarks on device only; it does not recognize/translate SASL, store/send frames, or assess signing. Existing measurements are a 23 October 2026 laptop Chrome result, not phone speed or accuracy.

## Ranked recommendations

Ranks are practical implementation order for the current learner journey, not official judging scores. “Likely owner” means a proposed integration owner; it does not change existing claims. Root owns router/provider/studio integration and camera policy under the connected-experience contract.

### 1. Make the motor and pump each teach one inspectable prediction-to-evidence loop

- **Learner problem:** A visually rich model can still leave the learner unsure what to change, what a reading means, or how to return to the source.
- **Interaction:** Show one learning question → invite an unassisted prediction → let the learner change one relevant input or select one part → show the calculated/illustrative result beside the visible settings → ask what evidence changed the prediction → link back to the relevant lesson/source. For motor, keep field speed distinct from actual shaft speed. For pump, preserve the prediction-before-reading step, reading/comparison, and report/export path.
- **Evidence and limits:** The PhET student-interview study reports that carefully structured guidance can reduce exploration of a well-designed simulation in that study context; it does not support pure discovery as a universal rule. Pair one gentle orientation with learner-selected exploration, then evaluate with learners. The existing motor/pump sources and disclosures are inspectable; no human learning gains have been measured. [PhET guidance study](https://phet.colorado.edu/publications/Paulson_etal_2009/Paulson_etal_2009.pdf), [PhET interface design interviews](https://phet.colorado.edu/publications/PhET_Interviews_I.pdf), local `docs/engineering/content-review.md` and Pump Lab source notes.
- **Likely owner/files:** Engineering/pump maintainers; candidate files `studio/src/engineering/teaching.ts`, `motorContent.ts`, `MotorScene.tsx`, `studio/src/pump-lab/PumpLab.tsx`, `readout.ts`, `report.ts`, `studio/src/studio-teaching-host/PumpHost.tsx`. Root owns cross-route lesson/source context.
- **Acceptance checks:** Actual component tests show the correct motor or pump question for the selected task; prediction precedes reading; changes update only supported model values; report records the displayed run; displayed limitations and citations remain visible; corrupt saved work is preserved. Later human/device acceptance compares learner ability to state what changed and why. Not run in this research pass.
- **Data/model/licensing:** Keep authored domain facts tied to existing source records and model assumptions. No new model or dataset is needed. Do not redistribute copyrighted source texts; link/cite permitted excerpts.
- **Judging connection:** Product, Usability, Creativity, Intelligence. Impact remains a hypothesis until learner testing.

### 2. Keep hints contextual, on demand, and clearly authored

- **Learner problem:** Generic or overly frequent guidance can interrupt inspection; ungrounded “AI tutor” language can imply the system evaluated the learner.
- **Interaction:** When the learner chooses a part or pump reading, show the exact context; offer a single low-reveal Hint action; ask the learner to predict/inspect; let them request another explanation if needed; keep the more detailed answer available after the prompt. Keep “Check” phrased as a self-explanation prompt until the learner can submit an answer that is actually evaluated.
- **Evidence and limits:** PhET interview work supports cautious scaffolding choices, not a universal hint dose. A study of help-seeking in the Andes step tutor found patterns consistent with students learning or recalling knowledge when they asked for help after minimal negative feedback, while repeated attempts without help often failed to repair errors; this is context-specific behavioral evidence, not proof for KAIRO or all learners. [PhET study](https://phet.colorado.edu/publications/Paulson_etal_2009/Paulson_etal_2009.pdf), [Ranganathan, VanLehn & Van de Sande](https://rptel.apsce.net/index.php/rptel/article/view/2014-09019).
- **Likely owner/files:** Studio teaching owner; `studio/src/studio-coach/model.ts`, `studio/src/learning-flow/StudioCompanion.tsx`, `studio/src/studio-guide-ui/StudioGuide.tsx`, plus deterministic `studio/tests/` tests. Avoid `TeacherProvider` or router changes without their owner.
- **Acceptance checks:** Actual `StudioCompanion` tests assert response content changes for each intent and selected part/readout; no hidden fault or answer is exposed before the intended step; unknown context produces a safe fallback; “Check” never claims a learner answer is correct without an answer/evaluator; sources and authorship label stay consistent. Not run here.
- **Data/model/licensing:** No model call required; use authored content and already-reviewed references. Any later model-backed explanation needs its own consent, source-grounding tests, quality evaluation and provider/data terms review.
- **Judging connection:** Product, Usability, Intelligence; do not claim trained personalization or measured gains.

### 3. Attach source provenance to the teaching statement, not just to the scene

- **Learner problem:** Seeing a source list separate from an explanation makes it hard to tell which claim came from a source, which is a property of the illustrative model, and which is a teaching prompt.
- **Interaction:** Keep one short “why this answer?” disclosure beside the response; distinguish (a) sourced fact and link, (b) calculated value with formula/inputs, (c) illustrative model assumption, and (d) authored coaching prompt. A changed reading should update the calculation context, not rewrite the original source statement.
- **Evidence and limits:** Source visibility is a design method, not evidence that a claim is correct or an extraction is complete. PhET's simulation-design research points to labels and limited strategically placed explanatory text as useful design features in its study context. The current motor/pump code and source review already provide meaningful provenance to build from. [PhET interface design interviews](https://phet.colorado.edu/publications/PhET_Interviews_I.pdf), `docs/engineering/content-review.md`, `studio/src/engineering/motorContent.ts`, `studio/src/pump-lab/physics.ts`.
- **Likely owner/files:** Domain-content owner and StudioGuide owner; candidates `studio/src/engineering/motorContent.ts`, `teaching.ts`, `studio/src/studio-teaching-host/packs/motor.json`, `packs/pump.json`, `StudioLessonPlan.tsx`, `StudioGuide.tsx`.
- **Acceptance checks:** Actual component render tests pair each factual claim with its source or explicitly label it as a model assumption; calculated claims show formula and active inputs; unsafe/invalid source links are omitted; empty provenance says none is available rather than inventing one. Review that motor speed language never implies measured shaft speed and pump readouts never imply real instrumentation.
- **Data/model/licensing:** Store bibliographic/link metadata and authored paraphrases, not textbook body or unlicensed diagrams. Validate source URL and reuse terms before copying assets/text.
- **Judging connection:** Product, Presentation, Intelligence, Sustainability.

### 4. Separate readable text, synchronized captions, voice, and translation in learner wording

- **Learner problem:** Choosing an Afrikaans/isiZulu/isiXhosa voice cannot translate an English lesson, and visible text alone is not synchronized caption evidence.
- **Interaction:** Keep the exact source passage and current English narration text visible; label it “Text KAIRO is reading” unless phrase/word synchronization is implemented. For translated help, let the learner select a cited source span, request a clearly marked draft in a chosen language, keep original and translation together, show the language tag, and retain an easy correction/return-to-source action. Never claim translation when only voice selection changed.
- **Evidence and limits:** WCAG requires captions for prerecorded audio in synchronized media at A, live captions at AA, and sign interpretation for prerecorded audio at AAA (the latter is not interchangeable with captions). W3C describes captions as a text equivalent for audio content; that does not certify KAIRO's current panel. The source shows `StudioGuide` renders response text but does not read `teacher.caption`, so current experience is readable persistent text, not synchronized speech captions. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [W3C captions overview](https://www.w3.org/WAI/media/av/captions/), [W3C sign-language criterion](https://www.w3.org/WAI/WCAG22/Understanding/sign-language-prerecorded.html), [SpeechSynthesisUtterance language property](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisUtterance/lang).
- **Likely owner/files:** Root/provider and lesson-language owner; `studio/src/teacher/TeacherProvider.tsx` (caption state, owned by provider owner), `studio/src/studio-guide-ui/StudioGuide.tsx`, `studio/src/learning-flow/StudioCompanion.tsx`, existing cited classroom translation path. Do not wire or change these files under this research claim.
- **Acceptance checks:** Actual component tests distinguish text-only from timed caption states; the caption matches the exact utterance/chunk being played if timing is shown; pause/stop/replacement clears stale caption state; the chosen device voice language is the language passed to this studio utterance (or the UI clearly explains that studio guidance is English); voice selection leaves source-language text unchanged; a draft translation retains source links and language metadata; errors preserve original passage. Later language review by fluent speakers is required. Not run here.
- **Data/model/licensing:** Voice providers receive selected text only with explicit existing consent; honor their service/data terms. Translation content needs source and reviewer provenance; do not claim qualified translation without a fluent reviewer. No SASL synthesis from spoken-language TTS.
- **Judging connection:** Usability, Impact, Presentation, Intelligence.

### 5. Preserve the two-step camera reveal and test all recovery branches before expanding access

- **Learner problem:** Camera permission is sensitive; surprise prompts, unclear denial, or a live stream that remains active after dismissal undermine trust and exclude learners without cameras.
- **Interaction:** Explain on an access page/dialog that the camera is optional and local tracking only → learner opens controls → learner presses Start → browser requests camera permission → clear starting/denied/unavailable/busy states → stop, close, Escape, route exit or tab hide releases capture → text/reading remains usable throughout.
- **Evidence and limits:** MDN documents HTTPS/secure-context and explicit user permission for `getUserMedia`, top-level/Permissions Policy restrictions, and browser permission indicators. W3C's modal pattern calls for focus entering the dialog, contained tab movement, Escape dismissal and return focus. Existing `AccessDialog`/`TrackingSession`/`lifecycle.ts` already encode much of this; this review did not test actual keyboard, assistive technology, camera permission or device cleanup. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [WAI modal-dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [W3C native dialog technique](https://www.w3.org/WAI/WCAG22/Techniques/html/H102).
- **Likely owner/files:** Root owns camera permission policy and dialog integration; `studio/src/learning-flow/AccessDialog.tsx`, `studio/src/signing/TrackingPanel.tsx`, `camera.ts`, `session.ts`, `lifecycle.ts`.
- **Acceptance checks:** Deterministic tests verify no media request before Start, video-only constraints, deny/unavailable/busy fallbacks, repeated Stop safety, and release after close/Escape/route exit/pagehide/track end; accessibility review verifies focus entry/trap/return and text alternative. A separate human/device pass must test actual browsers/permissions; not performed here.
- **Data/model/licensing:** Existing local model/runtime hashes, Apache-2.0 model card and version pins must remain auditable. Camera frames/landmarks stay on device; changing storage, telemetry, training or sharing requires a distinct consent and privacy/legal review.
- **Judging connection:** Usability, Sustainability, Impact, Product.

### 6. Offer links to vetted SASL learning materials; do not ingest them by default

- **Learner problem:** A learner asking about signing needs genuine SASL language materials and human interpretation, not a hand skeleton misrepresented as language.
- **Interaction:** In access help, distinguish “learn SASL” from “camera hand tracking.” Link out to an official/rights-holder resource with a clear external/opening label and cost/access note; keep source learning and text/reading available in KAIRO. Do not embed or cache dictionary clips unless the exact resource terms allow it.
- **Evidence and limits:** The Department of Basic Education hosts a SASL learning space and an LTSM catalogue addendum; SAnews/GCIS points learners to it and to the National Institute for the Deaf (NID) bilingual/video dictionary. NID describes a public/free subset as well as premium dictionary materials; its annual reports show vocabulary counts change over time. The license or embedding right for the dictionary video entries was not found in this research, so link to provider-hosted material only. [DBE SASL learning space](https://www.thutong.doe.gov.za/Default.aspx?alias=www.thutong.doe.gov.za%2Fsouthafricansignlanguage), [DBE LTSM catalogue](https://www.education.gov.za/Curriculum/LearningandTeachingSupportMaterials(LTSM).aspx), [NID resources](https://nid.org.za/resources/), [NID 2025 annual report](https://nid.org.za/wp-content/uploads/2025/10/Jaarverslag-2025-English-final.pdf), [GCIS resource note](https://www.sanews.gov.za/south-africa/learn-south-african-sign-language-and-help-break-barriers).
- **Likely owner/files:** Access content owner; candidate `AccessDialog.tsx`, plus a small reviewed resource metadata file under a future separately claimed scope. Preserve the existing `NID’s SASL resources` external link unless owner review finds it moved.
- **Acceptance checks:** Screen-reader and keyboard can identify that a link leaves KAIRO; verify destination is current official/resource-holder site; cost/access state is plain; a direct user's phrase “translate/sign” is met with truthful capability boundary and relevant text alternative; no video is bundled or silently downloaded.
- **Data/model/licensing:** No copying, caching, scraping, model training or in-app redistribution without the item-specific rights-holder licence and consent. Keep attribution, licence, checked date and expiry/review owner with any eventual entry.
- **Judging connection:** Product, Usability, Impact, Sustainability.

### 7. Treat SASL recognition/translation as a separate Deaf-led research gate

- **Learner problem:** 21 hand points and handedness are movement landmarks; they do not include the linguistic information, face/body grammar, regional variation or temporal context needed to translate SASL.
- **Interaction:** Continue to say “tracking only” in the existing camera preview. If a future KAIRO feature is considered: agree one narrow adult learner intent with Deaf SASL users → define a sign language-specific data/consent/rights plan → have Deaf participants create/review examples → build a signer-disjoint/device-disjoint test set → compare baseline and abstention/errors with human reviewers → only then consider an opt-in suggestion that requires learner confirmation. Keep unrecognized results unknown and retain typed/reading alternatives.
- **Evidence and limits:** Google's Hand Landmarker API returns hand keypoints; the model card is Apache-2.0 but says experimental and is not a sign-language model. W3C defines sign language interpretation as translation into a sign language, reflecting that it is linguistic translation, not geometry. UFS's 2025 project reports ethical data collection guidelines, data-sharing and a prototype app, while its public SASL HLT repository labels all content CC BY-NC-SA and lists end-to-end recognition/translation in its roadmap; this is a non-commercial research lead, not a commercially reusable tested translator. The Maswao GitHub README calls itself a weakly aligned SASL corpus pipeline built from YouTube sources, says clips are not redistributed due to rights/privacy, and leaves its citation/license details incomplete. Do not run the downloader or treat it as a permitted training set. [Google hand-landmarker guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker), [Google model card](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20Hand%20Tracking%20%28Lite_Full%29%20with%20Fairness%20Oct%202021.pdf), [W3C sign-language criterion](https://www.w3.org/WAI/WCAG22/Understanding/sign-language-prerecorded.html), [UFS project report](https://www.ufs.ac.za/templates/news-archive/campus-news/2025/june/ufs-project-paves-digital-path-for-south-african-sign-language), [UFS SASL HLT repository](https://github.com/ufs-za/human_language_technology_for_sasl), [Maswao dataset repository](https://github.com/dsfsi/maswo-south-african-sign-language-dataset).
- **Likely owner/files:** Separate Deaf-community research/ethics owner and SASL rights owner. No route or model files should change until that work publishes an approved interface and rights evidence. `studio/src/signing/` remains tracking only.
- **Acceptance checks:** Before any model test: written community-reviewed scope, item-level commercial licence and signer consent, validated labels/dialects, model card and hash, signer-disjoint evaluation including uncertainty/abstention, measured false accepts/rejects, correction/confirmation interface, accessibility fallback and privacy assessment. Nothing in this review satisfies these gates.
- **Data/model/licensing:** MediaPipe hand model's Apache licence covers the model artifact, not a SASL recognizer or signer recordings. UFS public repository terms are CC BY-NC-SA 4.0, not suitable for this commercial-product path without a formal agreement. Maswao source videos remain rights-holder/consent constrained. NID dictionary terms for ML use remain unverified. Obtain explicit training, inference and redistribution rights separately.
- **Judging connection:** Impact, Product, Intelligence, Sustainability. A future research opportunity, not a feature claim.

### 8. Measure mobile rendering and protect the 2D/reading fallback

- **Learner problem:** The richer 3D scene can consume battery, GPU time and mobile data; some devices cannot create WebGL or keep the scene smooth.
- **Interaction:** Start in diagram/reading mode on unsupported, narrow, reduced-motion or slow devices → offer the 3D view as an explicit optional enhancement → lazy-load only after selection → use a bounded resolution/quality tier → stop continuous work when static → report a clear fallback if context creation or scene loading fails.
- **Evidence and limits:** Pump Lab already selects the diagram by default for narrow/reduced-motion/no-WebGL cases, and the motor/avatar are lazily mounted. Motor R3F sets demand rendering and caps DPR by its current component setting. R3F/Three.js docs describe on-demand frames, resolution/pixel-ratio controls and explicit GPU resource disposal; these are implementation tools, not measured KAIRO phone performance. The separate hand-tracking package documents about 17.5 MB of local runtime/model assets; that is a useful transfer-size example, not a 3D avatar package size. [R3F performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance), [R3F pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls), [Three.js pixel ratio and disposal](https://threejs.org/docs/pages/WebGLRenderer.html), [Three.js resource disposal](https://threejs.org/manual/pages/how-to-dispose-of-objects.html), local `studio/src/signing/README.md`.
- **Likely owner/files:** Studio scene owners; candidates `studio/src/engineering/MotorScene.tsx`, `studio/src/pump-lab/PumpLab.tsx`, `PumpScene.tsx`, `studio/src/source-classroom/RainStage.tsx`, `StudioCompanion.tsx`. Root owns shared route/loading choices.
- **Acceptance checks:** Instrument cold asset bytes/time, route-to-interactive time, renderer FPS/frame-time distribution, peak memory, GPU context loss, and energy/thermal over a defined interaction on representative low/mid/high Android phones; test reduced motion, device rotation, background/return and WebGL-disabled fallback. Proposed hypotheses, not numeric commitments until baseline measurement. Keep all tasks usable via 2D/reading and compare rendering output for content parity.
- **Data/model/licensing:** 3D is primarily local CPU/GPU and network asset cost, not generative model cost. Verify model/texture/animation licences and cache semantics before shipping. No new package is recommended pending measurement.
- **Judging connection:** Usability, Sustainability, Presentation, Product, Creativity.
