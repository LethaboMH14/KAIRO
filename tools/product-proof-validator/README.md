# KAIRO claim evidence validator — isolated, read-only prototype (#43)

Run `node --test studio/tests/product-proof-validator.test.mjs` and `node tools/product-proof-validator/validate.mjs docs/product-proof-20261025/evidence/claims.example.json`. For public technical claims supply a **full 40-hex current integration commit** as the second CLI argument; a prior green branch SHA is not proof of the integrated tree. Node built-ins only; no GitHub API calls, file mutation, telemetry or learner data.

A registry has `claims: []`. Each claim requires stable `claimId`, statement, user job, evidence `status`, `publication` (`draft`/`public`), `claimClass` (`technical`, `user-experience`, `measured-outcome`, `research`), `judgingCriteria`, `sources` and `evidence`. Sources require issuer, HTTPS URL, publishedDate and checkedDate. Numeric records use `quantitative` with finite value, unit, positive denominator, period and method. Evidence kinds: `ci` (commit, runUrl, outcome), `review` (distinct reviewerSession and reviewUrl), `device` (device, observedAt, artifactUrl), `external-observation` (observedAt, method, sampleSize, redactedEvidenceUrl), `research` (issuer, url, checkedDate), and `synthetic` (test fixture only). The public gate rejects missing relevant evidence. A review session different from an author string is only a *declared* separation; this tool cannot authenticate reviewer identity. Similarly, a URL is a reference, not proof it contains what is claimed.

The validator **does not fetch** sources, authenticate CI, determine copyright permissions, validate consent, verify GitHub SHA reachability, inspect actual browser artifacts, estimate learning gains or grant merge/deploy permission. Never promote a claim based on this structural check alone. The example is a proposal, not a verified capability. Do not put personal interviews, learner content, emails or credentials into a source-controlled registry. Fail-closed secret-shaped scanning is heuristic; human privacy review remains mandatory.
